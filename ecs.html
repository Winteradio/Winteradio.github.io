ECS with Scene and Node

Entity는 이름표일 뿐이고, 실제 데이터는 Component가 들고 있다. Node는 System에 필요한 Component 조합을 정확히 묶어주고, 실행 순서는 사람이 손으로 짠 목록이 아니라 의존성 Graph가 정한다.

01

핵심 내용

왜 Node: Sparse Set은 Entity ID로 Component 하나만 접근 가능해서 여러 System이 걸치는 조합을 못 씀, Archetype은 조합이 하나 늘 때마다 새 Archetype과 데이터 복제가 필요함 — 데이터를 옮기거나 복제하지 않고 System별로 필요한 Component 조합만 선언하는 절충안으로 Node를 도입.
Node 멤버십은 자동으로 검증되지 않음.
Node는 ObjectPtr<T> 필드로 구성된 평범한 struct — 생성 시점에 수동으로 연결함. 프레임워크가 Entity의 Component를 스캔해서 확인해주는 과정은 없고, System이 사용 시점에 방어적으로 null 체크를 하는 게 실질적인 안전장치.
"필터링"은 Node 타입별 HashMap 하나일 뿐.
각 Node 타입은 자기만의 UUID → ObjectPtr<T> 저장소를 갖고, System은 그 Container를 그대로 받음. 프레임마다 훑으면서 필터링하는 과정은 없음.
의존성 Graph는 교과서적인 Kahn's Algorithm.
DependOn() 엣지로 진입 차수(in-degree) 맵을 만들고, 진입 차수 0인 System부터 Queue에 넣어 위상정렬. 순환이 있으면 조용히 실패 — 예외를 던지지 않고 로그만 남긴 뒤 빈 배열을 반환.

특징

Node가 Sparse Set과 Archetype의 트레이드오프를 둘 다 피함.
데이터를 옮기거나 복제하지 않고도 System이 필요한 Component 조합을 선언할 수 있어서, 라이트+렌더처럼 같은 Entity가 여러 System에 걸치는 경우를 자연스럽게 처리.
GC와 Reflection이 이미 통합됨.
PROPERTY()로 등록된 멤버는 자동으로 GC 추적 대상이 되어서, 수동 참조 카운팅 없이 도달 불가능한 Entity/Component가 정리됨.
실행 순서를 하드코딩하지 않음.
DependOn() 선언만 해두면 위상정렬이 알아서 순서를 정해서, System을 추가/제거할 때 다른 System의 실행 순서 코드를 손댈 필요 없음.

주요 내용

데모가 실제 API와 완전히 다름.
체크인된 코드에 없는 NodeRegistry/SystemRegistry/ DependOn 등을 데모가 그대로 참조 — 처음 이 프로젝트를 받은 사람은 데모조차 컴파일할 수 없음(이슈 #8보다 한 겹 더 깊은 불일치).
GC 등록을 빠뜨리면 컴파일 타임에 못 잡음.
PROPERTY()를 깜빡한 멤버는 조용히 GC 추적에서 빠져서, 다음 Collect() 때 예고 없이 해제됨 — 런타임에야 드러나는 종류의 실수.
Instance화되기 전까지는 안 드러나는 버그가 있음.
Entity::AddNode<T>()가 실제로는 Component 쪽에 등록되는 비대칭 버그, move 대입이 아무것도 move하지 않는 버그 등 — Template이라 실제로 그 경로를 쓰기 전까지는 조용히 묻혀 있었음.
02

상세 내용 & 다이어그램

Class 다이어그램 — Entity / Component / Node / System / Graph
Sequence 다이어그램 — World::Update() 한 틱
Entity/Component/Node/System은 전부 Object 하나를 상속하고, 저장은 Registry<Base> 하나가 담당.
초기 설계 노트에는 SceneManager/EntityManager/ComponentManager/SystemManager/NodeManager, 다섯 개의 전용 Manager가 따로 있었음. 지금 코드는 이걸 범용 Registry<Base> 하나로 합침 — 타입 해시를 키로 Container<T, Base>를 담는 HashMap 하나가 생성(Create<T>)·조회·삭제를 타입 구분 없이 전부 처리. 위 "주요 내용"의 데모-API 불일치는 정확히 이 리팩토링 전/후 API 차이 때문.
GC 도달 가능성은 범용 Property 순회.
Class별로 따로 짠 추적 함수가 아니라, TypeInfo의 Property 목록을 그대로 따라감. PROPERTY()로 등록하지 않은 ObjectPtr/RefPtr 멤버는 이 순회에 보이지 않음 — 아래 GC 함정이 예외적인 버그가 아니라 이 설계의 직접적인 결과인 이유.
GC는 PROPERTY()로 선언된 멤버만 추적함. Registry 멤버에 이걸 빠뜨리면 Collector가 도달 불가능하다고 판단해서, 다음 Memory::Collect() 때 조용히 해제해버림.
Class 다이어그램 — Registry<Base>/Container<T, Base> 실제 통합 구조

03

Sparse Set도 Archetype도 아닌 Node

방식문제점
Sparse Set빠르지만 Entity ID로 접근 가능한 Component가 하나뿐 — 모든 System이 Component 하나로 환원되지는 않음.
ArchetypeComponent 하나만 추가해도 새 archetype이 필요 — 기존 데이터를 복제해서 옮기고 원래 자리에서 지워야 함. 라이트+렌더 조합 하나 만들려고 해도 "Light Render Archetype"을 새로 만들어야 하는 식.
Node (이 프로젝트) Entity의 데이터를 옮기거나 복제하지 않고도 System이 필요한 Component 조합을 선언. 라이트+렌더 = 같은 Entity에 두 Node를 등록하고 Transform을 공유.

출처: 개인 리서치 노트, Entity Component System

버그

이번에 코드를 다시 읽으며 직접 찾아서 새로 이슈로 등록한 것들 — 상태는 실시간 동기화
실제 버그 7건 클릭해서 펼치기
#12 · include/Object/Entity.h:72 Entity::AddNode<T>()가 Node가 아니라 Component 쪽에 등록됨 버그 · 미수정
- Template 래퍼가 AddNode(nodeType) 대신 AddComponent(nodeType)를 호출함. 짝인 RemoveNode<T>()는 맞게 작성돼 있어서 더 눈에 안 띄는 비대칭 버그. 이 경로로 등록한 Node는 HasNode<T>()가 항상 false를 반환함.
#13 · src/Object/Entity.cpp:47-59 Entity의 move 대입 연산자가 실제로는 아무것도 move하지 않음 버그 · 미수정
- Object::operator=(other)가 lvalue를 받아 베이스 Class는 복사되고, m_name = std::move(m_name)은 other.m_name이 아니라 자기 자신을 self-move — 사실상 no-op. "move" 대입인데 이름은 그대로, UUID만 원본과 같은 값이 됨.
#14 · include/Graph/Graph.h:105,136,193 Graph의 BaseNode Template 인자가 Create()/Add()에서 무시됨 버그 · 미수정
- Graph<Base, BaseNode = GraphNode<Base>>는 커스텀 노드 타입을 받을 수 있게 설계됐고 m_nodeData도 HashMap<UUID, BaseNode>인데, Create()와 Add()는 둘 다 자기 BaseNode 대신 GraphNode<Base> node;를 하드코딩함. 기본값(BaseNode = GraphNode<Base>)으로 쓰는 한은 문제없지만, 실제로 커스텀 BaseNode를 넘기면 이 대입 자체가 컴파일되지 않음.
#15 · include/Graph/Graph.h:174-184 Graph::GetNode<T>()가 미스 시 공유 static Singleton을 반환 버그 · 미수정
- static GraphNode<T> null;은 같은 타입 T의 모든 조회 미스가 공유하는 함수-로컬 정적 변수. 호출자가 반환값에 SetDependency 등으로 쓰기를 하면, 그 타입에 대한 이후 모든 미스가 오염된 상태를 보게 됨.
#16 · include/Graph/Graph.h:18-28 GraphObserver::m_updated가 초기화되지 않음 버그 · 미수정
- 기본 멤버 초기화자가 없고 생성자는 = default. Graph::GetSorted()는 Add/Create가 한 번도 호출되지 않은 상태에서도 IsUpdated()를 읽어서, 첫 호출은 정의되지 않은 값을 읽는 셈.
demofile/main.cpp, SystemList.h, ComponentList.h, NodeList.h 데모가 실제로 존재하지 않는 API 전체를 호출 — 이슈 #8보다 한 겹 더 깊은 불일치 설계 노트
- ECS::NodeRegistry, ECS::ComponentRegistry, ECS::SystemRegistry, ECS::TypedSystem<Node>, System::DependOn/RemoveOn을 쓰지만 include/ 아래 어디에도 없음. 체크인된 코드는 범용 Registry<Base>와, 의존성 Graph API가 없는 추상 System<Base>뿐. ECS::Component/ ECS::Node도 기본 생성자만 선언하는데 데모는 ECS::Component(uuid)처럼 없는 생성자를 호출해서, 헤더를 복원해도 이 부분은 여전히 컴파일되지 않음.
Container/Storage.h:12-111 ObjectStorage<T>는 DataStorage<T>와 거의 동일한 미사용 죽은 코드 죽은 코드
- 유일한 차이는 ID 부여 방식뿐인 복붙 Class. ECS/데모 어디에서도 참조되지 않음.
