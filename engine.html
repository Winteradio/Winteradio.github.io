01 / INTRO

핵심 내용 & 전체 구조

Thread 5개가 각자 맡은 단계만 처리함 — 아래 그림 한 장이 엔진 전체임
왜 이 구조: OpenGL Context는 Thread 종속적이라 GPU 호출을 한 Thread에 몰아야 함 — World 시뮬레이션이 그 GPU 대기에 발목 잡히지 않도록, Unreal 스타일로 World/Render/RHI/Asset을 4개 Thread로 분리.
World는 렌더 타입을 절대 참조하지 않음.
ProxyComponent가 IsDirty()만 뒤집으면, Scene이 감지해서 Commander를 통해 스냅샷을 내보냄. World 코드 어디에도 렌더러 타입이 등장하지 않음.
RHI만 그래픽스 API를 직접 호출함.
OpenGL Context는 Thread 종속성이 있어서, 모든 GPU 호출은 Command 객체(실측 41개)로 감싸고 RHIWorker만 실행함.
RenderCommandList는 힙 할당이 거의 없음.
두 개의 LinearArena가 핑퐁 방식으로 동작 — World Thread가 하나에 람다를 쓰는 동안 Render Thread가 다른 하나를 비움.
100만 Instance 최적화의 진짜 병목은 "무조건 실행되는 삽입"이었음.
Dirty 추적용 HashSet::Insert가 프레임당 200만 번 무조건 호출되던 것을 if (!IsDirty()) 가드 하나로 5.4 → 22 FPS(Release)까지 끌어올림.

특징

World-Render 경계가 실제로 지켜짐.
렌더 타입을 아예 모르는 구조라, 렌더러를 통째로 교체해도(OpenGL→Vulkan) World/ECS 코드는 한 줄도 안 건드림 — 지금 Vulkan 백엔드를 별도 아키텍처 없이 기존 RHICommand/RHIWorker 위에 그대로 얹을 수 있는 것도 이 경계 덕분임.
vtable 없이 41개 Command를 함수 Pointer 하나로 Dispatch함.
CRTP 기반 RHICommand<T>라 실행 시점에 가상 함수 호출 Overhead가 없고, OpenGL Context는 RHIWorker Thread 하나로만 격리해서 Thread 안전성을 구조적으로 확보함.
실측 근거가 있음.
TransformPass(GPU Compute)로 50만 Instance, Hash Storm 가드로 5.4→22 FPS — 숫자로 뒷받침된 최적화 히스토리가 실제 Profiler 스크린샷과 함께 남아 있음.

주요 내용

라이트 하나짜리 데모에서는 안 드러나는 결함이 있음.
LightingPass Blending 버그가 대표적 — 실사용 시나리오(여러 라이트 동시)로 테스트하지 않으면 놓치는 종류의 문제임.
설계 초기 흔적이 여러 군데 남아 있음.
WorldCommandList(사실상 미사용), CullingPass·OverlayPass(미구현)처럼 구조는 있는데 내용이 없는 부분이 있어서, 코드만 보고 "이게 지금 쓰이는 경로인지" 판단하기 어려운 지점이 있음.
GC와 Vulkan, 둘 다 아직 절반임.
Memory Library는 이미 완성됐지만 엔진에 완전히 통합되지는 않았고(기능 현황 "진행 중"), Vulkan은 리소스 계층(메모리 · Buffer · Texture · Shader)까지 동작하고 Pipeline · RenderPass · Draw 경로는 아직 비어있음 — 그 전에 RHI 공용 계층부터 재설계하는 중.
02 / RESULTS

결과물

섀도우 매핑 · Deferred Rendering · 100만 Instance 최적화

성능 최적화 여정 — 100만 Instance 병목 추적기

이슈 #25 한 건에서 한 달(2026-04-22 ~ 2026-05-23)에 걸쳐 실제로 있었던 일임 — Profiler로 병목을 찾고, 고치고, 중간에 리팩토링으로 오히려 성능이 떨어지기도 하고, 다시 고치고, 다음 병목을 찾는 과정을 그대로 옮김.

1) 3만 Instance 회전 — Render Thread가 scalar GLM 행렬 곱에 발목잡힘.
Flame Graph에서 SceneProxy::UpdateRotation → UpdateTransform → glm::detail::mul4x4가 압도적 1위. GLM이 SIMD 없이 컴파일돼서 mat4×mat4가 전부 스칼라 루프로 도는 게 원인이었음.
2) 리팩토링 중 오히려 후퇴 — ISM 도입 과정에서 성능이 10배 나빠짐.
Unreal의 FInstancedStaticMeshSceneProxy를 참고해 InstancedStaticMeshProxy 개념을 도입하던 중, 이전 엔진이 100만 개 @ 20 FPS(Release)를 버텼던 반면 리팩토링 직후 버전은 10만 개에서야 20 FPS로 오히려 후퇴함 — 리팩토링이 항상 개선을 보장하지 않는다는 걸 Profiler가 바로 알려준 사례임.
3) TransformPass로 회복 + 그 이상 — TRS 행렬 계산을 GPU Compute Shader로 완전히 이전.
기존에는 MeshBatch 안에서 Instance마다 CPU로 Translation×Rotation×Scale 행렬을 만들었는데, 이제 local_size_x = 64 Compute Shader가 RawTransform SSBO(위치·쿼터니언·스케일)를 읽어 Transform SSBO(mat4)로 계산함. 결과: Debug 10만 개 안정 20 FPS(리팩토링 전에는 3만 개에서도 10 FPS 밑으로 떨어졌음), Release 50만 개 ~15 FPS.
4) 다음 병목까지 찾아둠 — HashTable::Rehash의 임시 배열이 Proxy 등록 시 힙 할당을 유발.
행렬 계산 병목이 풀리자 Profiler가 다음으로 HashTable::Rehash 내부의 임시 DynamicArray 생성을 새 할당 Hotspot으로 지목함. 다음 단계로 대량 삽입 전에 예상 용량만큼 Reserve를 미리 호출해서 Hot Path에서 Rehash 자체를 없애는 방향을 이슈에 남겨둠.
Hash Storm: 병목은 "무조건 실행되는 삽입"이었음.
100만 Instance에서 프레임당 200만 번 호출되던 HashSet::Insert를 if (!IsDirty()) 가드로 프레임당 1회로 축소: 5.4 → 22 FPS (Release).

04 / THREADING

Threading & 프레임 동기화

FrameGate — producer/consumer 조건 변수 쌍
FrameGate = 조건 변수 두 개 + atomic 프레임 차이.
Producer의 Submit()은 차이가 한도(3) 이상일 때만, Consumer의 Acquire()는 차이가 0일 때만 대기함 — 평소엔 atomic 값만 읽고 지나가서 락을 잡지 않음. World → Render(updateGate), Render → RHI(renderGate) 두 경계에 하나씩 있음.
RHIFrameExecutor는 RHICommandList 3개를 링으로 재사용함.
recordIndex는 Render Thread만, beginIndex는 RHI Thread만 씀 — 두 Thread가 같이 보는 건 atomic endIndex 하나뿐이고, acquire/release 순서로 기록 내용이 보이는 시점을 보장함. Mutex 없는 SPSC 구조.
종료는 깨우고 → 멈추고 → 놓는 순서.
Shutdown에서 두 Gate에 NotifyAll()을 먼저 걸어 대기 중인 Thread를 깨운 뒤 World → Asset → Render → RHI 순서로 Worker를 멈추고, RHICommandList를 쓰는 Worker가 전부 멈춘 다음에야 RHI Context를 놓음.

05 / MODULES

네 개의 Layer — 상세 내용 & Diagram

World는 렌더 타입을 모르고 · RHI만 그래픽스 API를 부름

WorldContext

Entity, Component, 그리고 밖으로 나가는 단방향 다리임. Scene::Flush()는 추가/삭제/갱신 3단계를 순서대로 도는데, 각 단계가 끝날 때마다 대상 HashSet을 비움.

ProxyComponent는 렌더러와 직접 대화하지 않음 — IsDirty()만 뒤집으면 Scene이 알아채고 Commander를 통해 스냅샷을 내보냄. Commander가 캡처하는 람다는 [renderView](Renderer*, RefPtr<RHICommandList>){ renderer->SetView(renderView); } 처럼 값 캡처 위주라 힙 할당이 거의 없음.

Renderer

RenderScene과 RenderGraph를 소유함 — 렌더링 쪽 객체는 전부 이 둘 중 하나를 거침.

(mesh, material) 조합 하나당 MeshDrawCommand 하나 → Draw Call 하나.
GeometryPass가 vertex layout + transform SSBO + 머티리얼을 바인딩하고, Batch 안의 모든 Instance를 인덱스 Draw 한 번으로 그림.
RenderPass는 ComputePass와 GraphicPass, 두 개의 추상 기반으로 나뉨.
ComputePass는 Compute Shader Dispatch만 담당하고, GraphicPass는 clear/depth/blend/ rasterizer 같은 Pipeline 상태 전체를 소유함.
RenderGraph는 실제로는 Graph가 아니라 고정된 체인임.
Transform→Shadow→Geometry→Lighting→Debug 순서로 SetDependency가 미리 걸려 있어서, "Graph" 구조인데 실제 파이프라인은 분기 없는 직선임.
TransformPass Dispatch는 1차원 고정 — 64 Instance당 Workgroup 1개.
groupX = ceil(instanceCount / 64), Y/Z는 항상 1. transform.cs.glsl의 local_size_x = 64와 맞물려 있는데, 생성자에서 넘기는 ComputePass(64, 64, 64) 그룹 크기는 아무 데서도 읽히지 않는 죽은 인자임 — Dispatch 시점에 로컬 상수 64를 다시 씀.
CullingPass는 Stub이지만 배선은 이미 되어 있음.
Draw()는 상태 체크만 하고 항상 true, GetResourceState()도 항상 eReady로 하드코딩. 다만 카메라/Indirect Draw Buffer/가시성 Buffer/AABB Buffer를 바인딩하는 SetCommand()는 이미 존재함. 짝을 이루는 culling.cs.glsl은 이름과 달리 Compute가 아니라 Vertex Shader 내용이라, Culling은 Shader·Dispatch·Pass 로직 전부 미구현 상태임.
OverlayPass는 완전히 빈 파일임.
OverlayPass.h/.cpp 둘 다 0바이트 — Class 선언조차 없는, 시작조차 안 된 자리표시자임.

GeometryPass가 한 프레임에 이 3개 채널을 GBuffer로 나눠서 씀 — LightingPass가 이 값들만 갖고 라이트별로 다시 계산. Position 채널은 실제로 저장되는 렌더 타깃이 아니라, Depth에서 그 자리에서 재구성한 디버그 시각화(이슈 #30 참고).

RHI

그래픽스 API를 직접 호출할 수 있는 유일한 Layer임. Command Class는 41개(초기화 11 · 갱신 3 · 리사이즈 2 · 제거 7 · Set 8 · Unset 7 · 프레임/Dispatch 3)이고, 전부 CRTP로 만든 RHICommand<T> 라 실행 시점엔 vtable이 아니라 함수 Pointer 하나로 Dispatch됨. 아래 다이어그램 3개는 master 기준(GLSystem이 RHISystem을 구현하던 구조)이고, 2026.10 재설계 후 구조는 Vulkan 절에 있음.

OpenGL Context는 Thread 종속성이 있어서, 다른 Thread에서 호출하면 정의되지 않은 동작이 됨. 모든 GPU 호출은 Command 객체로 감싸고 RHIWorker만 실행함.

리소스 삭제는 RHISystem이 즉시 지우지 않고, 7종 HashSet에 모아뒀다가 GLSystem::FlushPending()이 Flush 시점에 한 번에 처리함 — Thread 경계를 넘나드는 glDelete* 호출을 구조적으로 막는 장치.

Class 다이어그램 — GLSystem이 RHISystem을 구현하는 방식
Sequence 다이어그램 — 지연 삭제(FlushPending)

Vulkan 백엔드 & RHI 재설계 진행 중

Vulkan을 붙이면서 OpenGL에 맞춰져 있던 RHI 공용 계층을 Explicit API 기준으로 다시 짜는 중. 새 아키텍처를 따로 세운 게 아니라 RHICommand<T> 기록 · RHIWorker 실행 모델은 그대로 두고, 그 아래 (상태 · 바인딩 · 상수 · 백엔드 경계)를 바꾸는 작업임. 그림은 update/vulkan-rhi 브랜치 기준(2026.10).

여기까지 동작함: 초기화 · 프레임 루프 · 리소스 계층.
Instance/Device 선택, Surface/Swapchain, Primary/Secondary Command Buffer 분리(RHI Thread용 vs Worker별), Semaphore 2개 + Fence 1개로 acquire → submit → present, OUT_OF_DATE/SUBOPTIMAL 리사이즈 처리. 그 위에 Buffer · Texture 생성과 Staging 업로드, Buffer → Image 복사, Barrier, Sampler, VertexLayout, Shader(GLSL → SPIR-V 컴파일 후 SPIRV-Reflect로 입력 location과 바인딩 검증)까지 동작함.
지금 하는 중: Pipeline · RenderPass · Draw / Dispatch.
생성 함수 자리는 있지만 아직 비어 있음. 이걸 잇기 전에 공용 계층부터 바꾸는 중 — "슬롯에 꽂으면 끝"인 GL식 바인딩 모델로는 Vulkan의 Barrier와 Descriptor를 표현할 수 없어서.
VulkanMemory: 4MB 블록 + 블록 내부는 TLSFArena로 서브 할당.
메모리 속성(VkMemoryPropertyFlags)별로 고정 4MB VkDeviceMemory 블록을 필요할 때 만들고 비면 반환 — Resource마다 VkDeviceMemory를 따로 할당하는 흔한 Anti-pattern을 피함. 블록 내부 서브 할당은 Container Library의 TLSF 구현을 그대로 상속해서 씀.
상수: 낱개 Uniform → 이름 있는 UBO 블록 + 프레임 Ring Buffer.
CPU 쪽 사본과 비교해 바뀐 경우에만 Ring Buffer 슬라이스를 받아 기록하고, frameDiff보다 오래 안 쓴 블록은 회수함. 셰이더는 Common.glsl 한 파일에 BINDING_* 번호와 공용 구조체를 모아서 GL · Vulkan이 같은 소스를 씀.

Asset

3단계, 3개의 서로 다른 Thread — Parse가 메인 루프를 절대 막지 않고, Upload는 RHIWorker 밖에서 절대 실행되지 않음. 

eNone --TaskWorker.Parse()--> eLoaded --AssetCommander.Load() GPU 업로드--> (상태 전이 없음)
Parse = CPU 바운드, TaskWorker 풀(유휴 Worker가 있을 때만 — 없으면 AssetSystem Queue에 다시 넣어 다음 패스로 미룸)
Load  = GPU 업로드(AssetCommander), RHIWorker 전용
※ eAssetState는 eNone/eError/eLoaded/eExpried(오타)/eDirty뿐 — "완료(eReady)" 상태는 없고,
  준비 여부는 texture/buffer/shader Pointer가 non-null인지로 판단

설계가 바뀌어온 과정(RHI/Proxy 경계, FrameGate, RenderPass 전환, Vulkan)은 개발 히스토리에 커밋 날짜와 함께 정리해둠.

06 / FINDINGS

실제 코드에서 발견한 것들

설계 문서가 아니라 소스를 직접 읽고 확인한 내용 — 이후 고친 항목은 "수정됨" 표시

이 섹션은 Docs/Design_*.md 요약이 아니라, 2026.08 코드 리뷰 때 Engine/Private 과 Engine/Public의 실제 구현을 다시 읽으면서 확인한 내용임. 문서와 다른 부분, 그리고 흥미로운 설계 판단 몇 가지를 그대로 남겨둠.

LightingPass는 Blend를 켜지 않아서, 라이트가 여럿이면 마지막 라이트만 남음.
라이트 하나당 풀스크린 Quad Draw 한 번(Directional/Point/Spot Shader 분리)인데, GetPipeLine()이 채우는 RHIPipeLineCreateDesc에 blend 필드가 끝까지 비어 있음. 로컬로 RHIBlendState blendState; blendState.enable = false;를 선언은 하지만 어디에도 대입·전달되지 않는 죽은 코드임 — 이 구조가 성립하려면 Blend를 꺼야 하는 게 아니라 라이트별로 누적되도록 Additive Blending을 켜야 함. 라이트가 하나뿐인 데모에서는 드러나지 않는 버그임.
RenderGraph::Execute()는 Pass 하나만 준비 안 돼도 프레임 전체를 중단함.
정렬된 순서를 돌다가 어떤 Pass의 GetResourceState() != eReady 이거나 Draw()가 false를 반환하면 그 자리에서 루프를 break — 문제 있는 Pass 하나만 건너뛰는 게 아니라 이후 Pass 전부가 이번 프레임에 안 그려짐.
WorldCommandList는 사실상 미사용 상태임.
struct WorldCommand {}; 정도만 있고 WorldContext::Prepare() 는 그냥 // TODO. World→Renderer 트래픽은 전부 Commander/RenderCommandList로만 흐르고 있어서, 이 Class는 설계 초기 흔적으로 보임.
RHICommand 실제 개수는 41개임.
기존 설계 문서의 "45개 이상"이라는 서술은 실측과 다름 — 초기화 11 · 갱신 3 · 리사이즈 2 · 제거 7 · Set 8 · Unset 7 · 프레임/Dispatch 3.
RenderCommandList::ExecuteAll()에 기술적으로는 UB인 패턴이 있었음.수정됨 · #57
Task를 실행한 뒤 명시적으로 execute->~RenderTask()를 호출하고, 바로 다음 줄에서 execute->next를 읽었음. next가 trivial한 raw pointer라 실제로는 문제없이 동작했지만, 소멸자 호출 후 멤버를 읽는 건 엄밀히는 정의되지 않은 동작임 → 소멸자 호출 전에 next를 먼저 읽도록 바꿈.
Asset 파싱은 항상 병렬은 아니고, 기회적(opportunistic)임.
유휴 TaskWorker가 있을 때만 별도 Thread로 넘기고, 없으면 AssetSystem::AddTask()로 다시 Queue에 넣어 다음 패스로 미룸 — 동기적으로 직접 파싱하지 않고, "병렬 파싱"이 항상 보장되는 것도 아님.
Application/Engine 초기화 중 AssetWorker가 두 번 만들어졌음.수정됨 · #53
Engine::InitAsset()이 AssetWorker를 하나 만든 직후, InitWorker()가 SetTaskThread(4) 설정으로 또 하나를 만들어 m_assetWorker를 덮어씀 — 첫 번째 Instance는 조용히 버려졌음 → InitAsset()을 없애고 InitWorker() 한 곳에서만 만들도록 정리.
Win32Window의 WM_CLOSE 처리와 실제 종료 경로가 달랐음.수정됨 · #54
WndProc의 switch 문에 case 사이 break가 없어서, WM_CLOSE에서 설정한 m_status = eClosed가 같은 호출 안에서 곧바로 다시 eActive로 덮어써졌음. 실제 종료는 상태 체크가 아니라 close Callback → Engine::Shutdown() → m_window 리셋 → Run() 루프의 null 체크로 빠져나가는 경로로 이루어지고 있었음 → WM_CLOSE · WM_SIZE를 각자 case로 분리.
InputStorage는 더블 Buffer가 아니라 Lock-free Triple Buffer임.
m_InputData[3] — 메인 Thread가 쓰는 m_CurrData, 핸드오프용 atomic<InputData*> m_PrevData, WorldWorker가 읽는 m_LogicData. 256개 키코드 전체 상태를 4비트(Down/Press/Release/Repeat)로 패킹한 128바이트 배열로 저장함.
TaskWorker "풀"은 사실 AssetWorker 전용이고, 로드밸런싱이 없음.
TaskWorker 자체는 작업 하나짜리 Worker일 뿐 — "풀"은 AssetWorker가 가진 DynamicArray<RefPtr<TaskWorker>>이고, Thread 개수 4는 Engine.cpp에 하드코딩. 분배는 라운드로빈이 아니라 첫 번째로 유휴 상태인 Worker를 선형 탐색. Win32InputHandler의 입력 Queue도 Backpressure 없이 MAX_QUEUE_SIZE를 넘으면 그냥 통째로 비워 밀린 입력을 버림.
제네릭 Task<Args...>가 실제로는 두 가지 다른 방식으로 쓰임.
Task<Args...>는 std::function<void(Args...)> 얇은 Wrapper일 뿐인데, Asset/TaskWorker 쪽은 DefaultTask = Task<>로 인자 없이 Closure에 전부 캡처해서 쓰고, RenderTask : Task<Renderer*, RefPtr<RHICommandList>> 는 실제 인자를 받으며 커스텀 Allocator 위에 Intrusive List Node로 placement-new됨 — "제네릭" Template이 사실상 한쪽 전용 소비자를 위해 존재하는 셈임.
Asset 상태 머신에는 "완료(eReady)" 상태가 없음.
실제 eAssetState는 eNone / eError / eLoaded / eExpried(오타) / eDirty 뿐임. GPU 업로드(AssetCommander::Load) 이후 별도 상태 전이가 없어서, 준비 여부는 상태값이 아니라 texture/buffer/shader Pointer가 non-null인지로 다른 코드가 추론함.
RHIDrawIndexDesc / RHIDispatchDesc가 자기 태그 대신 남의 태그를 썼음.수정됨 · #55
eResourceType은 9개 값(Buffer/Texture/Sampler/Shader/PipeLine/ Layout/Target/Const/Pass)이 따로 있는데, RHIDrawIndexDesc는 eLayout을, RHIDispatchDesc는 ePipeLine을 그대로 재사용했음 — Draw Command와 VertexLayout이 desc.type 값만으로는 구분되지 않았음 → eGraphics / eCompute 태그를 새로 추가.
PNGParser에 타입이 어긋나는 버그가 있었음.수정됨 · #56
stbi_load_from_memory는 항상 8비트 데이터를 반환하는데, componentType은 소스에 따라 eFloat/ eUInt로 설정됐음. sRGB 판별도 IHDR 바로 다음 청크 하나만 검사했음 → 16비트 PNG는 stbi_load_16 경로로 분기하고 componentType을 실제 비트 수에 맞춤, sRGB 판별은 IHDR ~ IDAT 사이 청크를 전부 검사하도록 바꿈.

08 / ISSUES

해결한 이슈

저장소 이슈 트래커와 디버그 로그 기준

섀도우 acne / NaN / 깜빡임 해결

증상
카메라 회전 중 간헐적으로 물체 전체가 검게 표시됨. RenderDoc 단일 프레임 캡처에서는 정상.
원인
grazing 각도에서 RPDB depth-bias의 분모(det)가 0에 가까워지며 NaN이 발생, FragColor까지 그대로 전파됨.
해결
NaN을 사후에 가리려 하지 않고 발생 자체를 차단(safeDet = mix(EPSILON, det, step(EPSILON, abs(det)))) — 곱셈이나 mix로는 NaN을 지울 수 없기 때문. grazing 컷오프도 맨 끝에서 한 번만 곱하도록 이동(dFdx 앞에서 분기하면 GLSL에서 undefined behavior).

Multi-proxy dirty flag race 해결

증상
같은 Transform을 공유하는 라이트와 메시를 가진 Entity가, 첫 프레임 이후 둘 중 하나의 업데이트를 조용히 멈춤.
원인
Hash Storm 최적화의 if (!IsDirty()) OnUpdate() 가드가 공유 Component에 있던 dirty 플래그를 지워버림 — 먼저 처리된 Proxy가 둘 다의 플래그를 지운 셈.
해결
Proxy별 dirty 세대(generation) 카운터 도입: Component는 변경 시 세대 번호만 증가시키고, 각 Proxy가 자신이 마지막으로 본 세대를 독립적으로 추적.

Point Light 입사 방향 아티팩트 미해결

증상
표면 아래에 위치한 라이트가, 라이트 볼륨 경계 부근에서 오히려 표면을 더 밝게 만듦.
원인
Two-sided 라이팅 보정의 max(dot(normal, rayDir), 0.0)가 이 경우 0으로 클램프되어, 입사 방향 보정이 아예 걸리지 않음.
개선 방향
보정을 fragment→light가 아니라 light→fragment 방향으로 계산. 섀도우 맵이 도입되면 이 케이스는 자연스럽게 가려지기도 함.
09 / NOTES

기술 노트

구현하면서 직접 유도/정리한 그래픽스 이론 — 이슈 트래커에 전문을 남겨둠
#30 Position Reconstruction from Depth Buffer
- 왜: 1920×1080에서 Position GBuffer(RGBA32F)만 프레임당 ~31MB. Frostbite/UE4/5/CryEngine 전부 Position 채널을 버리고 Depth에서 역산함.
- 어떻게: World → View → Clip → (÷w) → NDC → Depth 순서를 거꾸로 밟아 복원. 핵심은 Position이 동차좌표에서 항상 w=1이라는 불변식.
- 사이트 GBuffer 스크린샷의 "Position" 채널도 실제로 저장되는 렌더 타깃이 아니라, 디버그 시각화 Pass가 Depth로부터 그 자리에서 재구성한 것임.
#37 Quaternion Rotation Matrix Derivation
- 쿼터니언 샌드위치 곱 q·v·q*이 3×3 회전 행렬과 같다는 걸 직접 손으로 증명 — 곱 전개 → Rodrigues 형태 변환 → Vector 연산을 행렬로 변환 → 쿼터니언 성분 대입, 4단계로 진행.
- Library(GLM 등)가 이미 해주는 변환을 그대로 쓰지 않고, 왜 그 공식이 맞는지 끝까지 손으로 따라간 기록임.
#39 Point Light & Phong Specular 정리
- GLSL reflect(I,N) = I - 2·dot(N,I)·N가 교과서 공식과 부호만 다르다는 것, 그리고 faceforward로 normal을 뒤집어도 반사 Vector 자체는 바뀌지 않는다는 걸 정리(NdotL 부호에만 영향).
- 라이트가 표면 안쪽에 있는 two-sided 케이스 3가지 방법을 비교: abs(NdotL)(specular 방향이 틀어짐) → faceforward(diffuse만 고침) → incidentDir 보정(권장 — 입사 방향 자체를 표면 앞쪽으로 재계산). 이 세 번째 방법이 실제로 채택된 방향이고, engine.html의 "Point Light 입사 방향 아티팩트" 이슈와 이어짐.
- 감쇠식은 1/(d²+1)로 d→0 발산을 막고, range 기반 falloff를 곱해 range 밖에서 매끄럽게 0이 되도록 함.
#48 Directional Light Shadow Mapping — 종합 정리
