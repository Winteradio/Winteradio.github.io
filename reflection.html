C++17 Reflection

GENERATE / PROPERTY / METHOD — Unreal의 UCLASS/UPROPERTY/UFUNCTION 참고함. C++17 inline static로 타입/멤버/Method를 컴파일 타임에 등록 — 헤더만으로 완결되고 링커 에러 없음.

01

핵심 내용

왜 직접 만들었는지: C++ 표준 RTTI는 타입 이름과 다운캐스트 정도만 줄 뿐 프로퍼티 목록을 안 줘서 GC 순회·직렬화에 못 씀 — Unreal의 UHT 같은 별도 코드 생성 툴 없이, Macro와 Template만으로 컴파일 타임에 타입 정보를 등록하는 STL 비의존 RTTI 대체 시스템을 택함.
단일 상속 체인만 지원 — 그래서 Cast<T> 안전함.
TypeInfo는 Class당 SuperType 하나만 모델링함. 위로 올라가는 경로가 하나뿐이라 Cast<T>는 DAG 탐색이 아니라 체인을 걷는 것으로 끝남 — dynamic_cast가 전혀 필요 없음.
Container 순회는 힙 할당 0임.
Iterator가 64바이트 고정 버퍼에 실제 STL/wtr 반복자를 placement-new로 생성 — vtable 대신 함수 Pointer 6개로 디스패치함.
같은 시그니처의 함수 두 개도 서로 다른 static 객체를 가짐.
MethodCreator<Func, func>가 함수 Pointer "값"을 비타입 Template 파라미터로 받음 — 시그니처가 같아도 함수마다 별도 Template Instance → 별도 static이 생김.

특징

Macro 하나로 보일러플레이트를 거의 다 없앰.
GENERATE/PROPERTY/METHOD만 붙이면 등록 코드를 손으로 안 써도 됨 — 컴파일 타임 빠른 경로와 런타임 SuperType 워크를 나눠서 평소엔 dynamic_cast보다 빠름.
런타임 오버헤드를 설계 단계에서부터 줄이려 한 흔적이 뚜렷함.
64바이트 SBO Iterator(힙 할당 0), 비타입 Template 파라미터로 new 없는 정적 MethodCall 등 — "Reflection은 느리다"는 통념을 구조적으로 반박하려는 선택들임.
Get/Set의 타입 안전성 기준이 명확함.
Get은 상속 관계를 허용하고 Set은 완전히 같은 타입만 허용 — object slicing이나 의도치 않은 다형성 허용 같은 위험을 원천 차단하는 규칙이 문서에 남아 있음.

주요 내용

크로스플랫폼 검증이 안 되어 있었음.
Utils.cpp가 Windows 아닐 때 GetName 대신 이름이 다른 GetClassName을 정의 — GCC/Clang 빌드는 TypeInfo::Get<T>()를 쓰는 순간 링크 실패함. Linux/Mac에서 한 번도 안 돌려봤다는 뜻.
Method 쪽은 Property만큼 타입 검증이 엄격하지 않음.
MethodInfo::Invoke가 소유 Class를 검증하지 않음 — 시그니처만 같으면 서로 무관한 Class끼리도 조용히 타입 펀될 수 있음.
Template Class 조합에서 Macro가 깨질 수 있음.
Template Class 내부의 PROPERTY()가 GCC/Clang의 공격적인 dead-code elimination에 스트리핑되는 문제가 아직 완전히 해결되지 않음(이슈 #25).
02

상세 내용 & 다이어그램

단일 상속만 지원 — 그래서 Cast<T> 안전함
클래스 다이어그램 — 등록 구조
시퀀스 다이어그램 — 매크로 등록부터 런타임 Cast/조회까지

사용 예시

class ObjectB : public ObjectA
{
    GENERATE(ObjectB);
public:
    PROPERTY(m_intValue);
    int m_intValue = 0;

    PROPERTY(m_array);
    wtr::DynamicArray<int> m_array; // Container도 자동 감지

    METHOD(Add);
    int Add(int a, int b) const { return a + b; }
};

// 런타임 조회 — 이름 문자열로 Property/Method에 접근
const auto* type = obj->GetTypeInfo();
const auto* prop = type->GetProperty("m_intValue");
prop->Set(obj, 42);            // 컴파일 타임 오프셋으로 직접 메모리 접근, dynamic_cast 없음

const auto* method = type->GetMethod("Add");
int result = method->Invoke<int>(obj, 3, 4);  // MethodCreator가 함수 Pointer별 static 생성

03

매크로가 실제로 확장되는 방식

GENERATE(ClassName)

SuperType 탐지
Utils::TypeDetector의 SFINAE로 베이스의 Reflection 태그를 찾아 SuperType으로 alias함. ThisType은 Class 자신을 가리킴.
GetTypeInfo() Override
함수 지역 static const TypeInfo*("magic static", Thread 안전, 최초 1회만 초기화)를 Override된 virtual이 반환함 — 베이스 Pointer가 런타임에 실제 파생 타입을 복원하는 방법.
자체 등록
inline static const TypeInfo* s_typeInfo = GetStaticTypeInfo(); — 정적 초기화 시점에 동적 초기자가 실행되고, TypeInfo 생성자 마지막에서 TypeManager::Regist(this)를 호출해 unordered_map 에 등록함. TypeManager::GetHandle()이 Meyer's Singleton이라 TU 간 정적 초기화 순서 문제에서 자유로움.
이름 붙은 링커 위험 요소
__STATIC_USED__(GCC/Clang의 __attribute__((used))) 가 "참조되지 않는" static이 스트리핑되는 걸 막으려고 존재 — 늘 이기는 건 아님(아래 이슈 참고).

PROPERTY(member)

오프셋 캡처
offset = reinterpret_cast<size_t>(&(static_cast<Class*>(nullptr)->*pointer)) — null 베이스 Pointer를 통해 멤버 Pointer를 역참조함. vtable이 있는(non-standard-layout) Class에서는 offsetof가 지원되지 않아 필요한 방식.
Get/Set
둘 다 reinterpret_cast<char*>(instance) + m_propertyOffset 으로 해석됨. 대입은 캡처 없는 람다가 void(*)(void*, const void*) 썽크로 decay되어 *(Property*)dest = *(const Property*)src를 수행.
Sequence 다이어그램 — Set()의 타입 안전성 분기(Pointer는 상속 허용, 값 타입은 완전 일치만)

METHOD(name)

호출 대상은 Type Erasure로 지워짐.
MethodBase(빈 껍데기) → MethodCall<Return, Args...>(순수 가상 Invoke) → MemberMethodCall/ StaticMethodCall(실제 함수 Pointer 보관) 3단 상속으로, 호출부는 Return/Args만 알면 됨.
MethodCreator<Func, func>가 함수 Pointer "값"을 Template 파라미터로 받음.
같은 시그니처의 함수라도 func이 다른 값이면 서로 다른 Template Instance — 함수마다 자기 static MemberMethodCall을 따로 가짐(부분 특수화 3개: 멤버/const 멤버/정적 함수).
Class 다이어그램 — MethodBase 상속 구조와 MethodCreator

Zero-allocation Container Iterator

vtable도 베이스 Class도 없음
alignas(void*) uint8_t m_storage[64]에 함수 Pointer 6개 (Next/Prev/Destroy/Element/Copy/Compare) — Container 타입별로 고정된 이 함수 Pointer 묶음 자체가 수동으로 만든 vtable임.
생성
begin()이 실제 STL/wtr const_iterator를 64바이트 버퍼에 placement-new로 직접 생성함.
복사는 진짜 깊은 복사임
버퍼를 그냥 memcpy하면 내부 Pointer(해시 버킷, 리스트 Node)를 들고 있는 반복자가 깨짐. CopyFunc가 원본에서 새로 placement-new함.
소멸은 명시적
uint8_t[]는 소멸자를 자동으로 안 불러줌 — ~Iterator()가 DestroyFunc를 호출해 그 자리에서 실제 반복자의 소멸자를 실행함.
04

결과물 / 이슈

#25 PropertyInfo missing in template classes on GCC/Clang 미해결
- 원인: PROPERTY()가 Template Class 내부에 만드는 static 객체가, Template이 겉보기에 안 쓰이는 것처럼 보이면 GCC/Clang의 공격적인 dead-code elimination에 의해 조용히 스트리핑되어 Property/GC 등록이 깨짐.
- 개선 방향: 컴파일러 used/retain 속성으로 강제 보존 — __STATIC_USED__가 노리는 것과 같은 종류의 해법이지만 아직 Template까지는 완전히 커버하지 못함.
#29 TypeInfo initialization failure with forward declarations 해결
- 원인: TypeInfo<T>는 Metadata 추출을 위해 컴파일 타임에 완전한 타입의 크기/정렬 정보가 필요한데, 전방 선언만으로는 이걸 제공할 수 없음.

버그

이번에 코드를 다시 읽으며 직접 찾아서 새로 이슈로 등록한 것들 — 상태는 실시간 동기화
실제 버그 3건 클릭해서 펼치기
#31 · src/Utils.cpp:9,53, include/Type/TypeInfo.h:93 Windows 밖에서는 링크가 안 됨 — GetName 정의가 아예 없음 버그 · 미수정
- TypeInfo.h:93은 플랫폼 무관하게 Utils::GetName(...)을 호출하는데, Utils.cpp는 #if defined(_WIN32)일 때만 GetName을 정의하고 #else 분기는 이름이 다른 GetClassName을 정의함. GCC/Clang 빌드는 TypeInfo::Get<T>()를 Instance화하는 순간 "undefined reference"로 링크 실패 — #25/#29와는 별개인, 아직 등록되지 않은 빌드 차단 버그.
#32 · include/Method/MethodInfo.h:77, MethodCall.h:117 MethodInfo::Invoke가 소유 Class를 검증하지 않음 버그 · 미수정
- 시그니처(Return/Args)가 같으면 서로 무관한 두 Class의 Method가 같은 MethodCall<Return,Args...> TypeInfo로 묶여 Cast를 통과함. MemberMethodCall::Invoke는 전달받은 Pointer를 그냥 static_cast<ClassType*>해서 호출 — PropertyInfo와 달리 런타임 타입 체크가 없어서, 잘못된 Class의 Instance를 넘기면 조용히 타입 펀됨.
include/Type/TypeInfo.h:110, src/Type/TypeManager.cpp:34-37 TypeManager의 map 키가 사실상 Pointer 자기 자신 + 락 없는 조회 설계 노트
- m_typeHash는 reinterpret_cast<size_t>(this) — 이름 기반 해시가 아니라 TypeInfo 객체 자신의 메모리 주소임. ASLR 때문에 프로세스마다 값이 달라져 직렬화/프로세스 간 식별에는 못 씀. GetTypeMap()도 락 없이 원본 map을 그대로 반환해서, Regist()가 거는 뮤텍스와 별개로 순회 중 경합이 가능함.
